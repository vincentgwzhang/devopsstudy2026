DevOps Observability Study Repository

This repository is a Spring Boot microservices study project focused on modern DevOps observability. It demonstrates how a request flows through several services and how traces, metrics, logs, and alerts can be collected and viewed with common open-source tools.

Spring Boot Microservices Distributed Tracing OpenTelemetry Zipkin Jaeger

1. What This Repository Demonstrates

The application is intentionally small, but it models a realistic service-to-service call chain: 

Postman / Browser
        |
        v
GatewayService
        |
        v
OrderService
        |
        v
PaymentService
        |
        v
BankService

Each service is a separate Maven module. The services communicate through direct HTTP calls, and the tracing setup shows how one incoming request becomes a full distributed trace across the whole chain.

  • GatewayService receives the external request and routes it to OrderService.
  • OrderService creates an order and calls PaymentService.
  • PaymentService authorizes a payment and calls BankService.
  • BankService simulates the final bank transfer settlement.
  • CommonModule contains shared tracing helpers for MDC log enrichment.

2. Observability Concepts

Observability is usually built from three major signal types:

  • Traces: show the path of one request across multiple services.
  • Metrics: show system-level trends such as latency, error rate, throughput, CPU, memory, and JVM behavior.
  • Logs: provide detailed event-level information for debugging a specific failure or behavior.

In this project, tracing is the main focus, but the repository also provides a good base for learning Prometheus metrics, centralized logging, dashboards, and alerting.

3. Solution A: Direct Zipkin Export

The simplest tracing setup is to configure every microservice to export spans directly to Zipkin from its own application.yml. 

GatewayService  ----\
OrderService     ----> Zipkin
PaymentService  ----/
BankService     ---/

With this setup, Zipkin receives spans from each service and reconstructs the full call graph by using traceId, spanId, and parentSpanId.

  • traceId identifies one complete distributed request.
  • spanId identifies one operation inside that request.
  • parentSpanId links one span to the upstream operation.
  • Zipkin UI can be used to search by service, operation, duration, or trace id.
This approach is easy to understand and good for learning, but each application is coupled directly to the tracing backend.

4. Solution B: OpenTelemetry Collector Fan-Out

A more flexible architecture is to make every service export telemetry to the OpenTelemetry Collector. The Collector then forwards traces to one or more backends. 

Spring Boot services
        |
        | OTLP HTTP / OTLP gRPC
        v
OpenTelemetry Collector
        |
        +--> Zipkin
        +--> Jaeger
        +--> Tempo
        +--> Commercial or cloud observability platforms

This is the key design idea: services only know the OTLP endpoint of the Collector. The backend choice becomes infrastructure configuration instead of application code.

4.1 OpenTelemetry Collector + Zipkin

The Collector receives OTLP traces and exports them to Zipkin. Zipkin still provides the trace storage and UI experience. 

Microservice -> OTLP -> OpenTelemetry Collector -> Zipkin UI

4.2 OpenTelemetry Collector + Jaeger

Jaeger is a classic distributed tracing platform. The all-in-one image is convenient for local study because it includes collection, query, storage, and UI components in one container. 

Microservice -> OTLP -> OpenTelemetry Collector -> Jaeger -> Jaeger UI

A common local Jaeger UI endpoint is http://localhost:16686.

4.3 OpenTelemetry Collector + Tempo + Grafana

Grafana Tempo is a trace backend from Grafana Labs. Tempo itself is focused on storing and querying traces; the UI is normally provided by Grafana. 

Microservice -> OTLP -> OpenTelemetry Collector -> Tempo -> Grafana UI

This combination is useful when you want traces, Prometheus metrics, and Loki logs to be explored from the same Grafana interface.

4.4 Other OpenTelemetry Targets

Category Examples Purpose
Open-source trace backends Zipkin, Jaeger, Grafana Tempo Good for local learning, self-hosted environments, and platform engineering.
Commercial observability platforms Datadog, New Relic, Dynatrace, Honeycomb, Splunk Observability Provide managed APM, dashboards, traces, logs, metrics, and alerting.
Cloud-native tracing services AWS X-Ray, Google Cloud Trace, Azure Monitor Useful when the application is deployed on the corresponding cloud platform.
Streaming and buffering layer Kafka Telemetry can be written to Kafka first and consumed by downstream observability systems later.

5. Metrics With Prometheus

Prometheus is commonly used for metrics. In a Spring Boot application, the usual path is to enable Spring Boot Actuator and expose a Prometheus-compatible endpoint. 

Spring Boot Actuator /actuator/prometheus
        ^
        |
Prometheus scrape

A typical setup includes:

  • Add spring-boot-starter-actuator and the Micrometer Prometheus registry.
  • Expose /actuator/prometheus.
  • Configure Prometheus scrape targets for the services.
  • Use Grafana dashboards to visualize JVM, HTTP latency, request rate, and error rate metrics.

Prometheus is not meant to show the full path of one request. It is better for trends, SLOs, dashboards, and alert conditions.

6. Logs With Loki, Fluent Bit, and Grafana

A common open-source logging stack is Loki + Fluent Bit + Grafana. 

Spring Boot logs
        |
        v
Fluent Bit
        |
        v
Loki
        |
        v
Grafana
  • Spring Boot logs should include useful context such as traceId and spanId.
  • Fluent Bit collects container or file logs, adds labels, and forwards them to Loki.
  • Loki stores and queries logs using labels and LogQL.
  • Grafana provides the UI for querying logs and correlating them with metrics and traces.
When logs contain trace ids, it becomes much easier to jump from a trace to related logs, or from an error log back to the trace.

7. Other Practical DevOps Designs

7.1 Alerting With Prometheus and Alertmanager

Metrics become more useful when they can trigger alerts. Prometheus evaluates alert rules, and Alertmanager handles grouping, deduplication, silencing, and notification delivery. 

Prometheus rules -> Alertmanager -> Slack / Email / PagerDuty

7.2 Health Checks for Kubernetes

Spring Boot Actuator health endpoints can be used with Kubernetes readiness and liveness probes. Readiness decides whether a pod should receive traffic. Liveness decides whether a pod should be restarted. 

Kubernetes probe -> /actuator/health -> route traffic or restart pod

8. Recommended Learning Path

  1. Start with direct Zipkin export to understand traceId, spanId, and parent-child span relationships.
  2. Add the OpenTelemetry Collector and move applications to OTLP export.
  3. Fan out traces from the Collector to Zipkin and Jaeger, then compare their UIs.
  4. Try Tempo with Grafana to understand the Grafana observability ecosystem.
  5. Add Prometheus for metrics and Loki for logs to complete the observability picture.

A mature local architecture can look like this:

Spring Boot services
        |
        +--> traces  -> OpenTelemetry Collector -> Zipkin / Jaeger / Tempo
        |
        +--> metrics -> Actuator -> Prometheus -> Grafana
        |
        +--> logs    -> Fluent Bit -> Loki -> Grafana
        |
        +--> alerts  -> Prometheus rules -> Alertmanager
