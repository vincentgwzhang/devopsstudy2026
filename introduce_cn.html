DevOps Observability 方案总结

这个项目是一个 Spring Boot 微服务链路：GatewayService 调用 OrderService，OrderService 调用 PaymentService， PaymentService 再调用 BankService。它很适合用来学习现代 DevOps 里的 Observability：Tracing、Metrics、Logs 以及 Alerting 怎么组合起来。

Distributed Tracing Metrics Logs OpenTelemetry Spring Boot Actuator

1. Observability 的三大核心

Observability 通常可以拆成三类数据：

  • Traces：一次请求经过了哪些服务，每一步花了多久，哪里慢了或失败了。
  • Metrics：系统整体状态，例如 QPS、错误率、响应时间、CPU、内存、JVM 指标。
  • Logs：服务运行过程中打印的详细事件，适合排查具体错误上下文。

这三类数据并不是互相替代的关系。Tracing 适合看一次请求的路径，Metrics 适合看整体趋势和告警， Logs 适合看具体错误原因。真实生产环境一般会三者一起使用。

2. Zipkin：应用直接上报 Trace

第一种方案是每个 microservice 在自己的 application.yml 里直接配置 Zipkin 地址。 应用启动后，Spring Boot、Micrometer Tracing 和相关 exporter 会把 span 直接发送给 Zipkin。 

GatewayService  ----\
OrderService     ----> Zipkin
PaymentService  ----/
BankService     ---/

这种方案的优点是简单、直观，适合学习分布式链路追踪的基本概念：

  • traceId 表示一次完整调用链。
  • spanId 表示调用链里的某一个步骤。
  • parentSpanId 表示当前 span 的上游 span。
  • Zipkin UI 可以按 service、trace id 查询完整调用链。

缺点是应用和后端绑定得比较紧。如果以后从 Zipkin 换成 Jaeger、Tempo 或云厂商平台，需要改每个服务的配置。

3. OpenTelemetry Collector：统一接收和分发

第二种方案是让所有 microservice 只连接 OpenTelemetry Collector。应用只需要把 trace/span 通过 OTLP 发送到 Collector，Collector 再负责转发到 Zipkin、Jaeger、Tempo 或其他平台。 

Spring Boot services
        |
        | OTLP HTTP / OTLP gRPC
        v
OpenTelemetry Collector
        |
        +--> Zipkin
        +--> Jaeger
        +--> Tempo
        +--> Cloud observability platform

这个设计更接近企业里的常见做法，因为它把应用和可观测性后端解耦了。

3.1 OTel + Zipkin

应用把 trace 发给 Collector，Collector 使用 Zipkin exporter 转发给 Zipkin。 Zipkin 继续负责存储和 UI 查询。 

Microservice -> OTLP -> OpenTelemetry Collector -> Zipkin UI

3.2 OTel + Jaeger

Jaeger 是经典的分布式 tracing 系统，常用 all-in-one 镜像可以直接提供 Collector、Query 和 UI。 Jaeger UI 默认常见端口是 16686。 

Microservice -> OTLP -> OpenTelemetry Collector -> Jaeger -> Jaeger UI

Jaeger 适合学习 service、operation、trace 查询，也适合对比 Zipkin 和 Jaeger 两种 UI 的不同。

3.3 OTel + Tempo + Grafana

Tempo 是 Grafana Labs 的 trace backend。Tempo 本身重点是接收、存储和查询 trace，不提供像 Zipkin 那样的独立完整 UI。通常需要通过 Grafana 查看 Tempo 里的 trace。 

Microservice -> OTLP -> OpenTelemetry Collector -> Tempo -> Grafana UI

Tempo 的优势是和 Grafana 生态结合得很好，可以和 Prometheus metrics、Loki logs 在 Grafana 里做关联分析。

3.4 OTel 还能分发到哪些产品

类型 常见后端 说明
开源 Trace 后端 Zipkin、Jaeger、Grafana Tempo 适合本地学习、私有化部署和平台化建设。
商业 Observability 平台 Datadog、New Relic、Dynatrace、Honeycomb、Splunk Observability 通常提供 traces、metrics、logs、APM 和告警的一体化能力。
云厂商平台 AWS X-Ray、Google Cloud Trace、Azure Monitor 适合部署在对应云平台上的服务。
消息队列和中转层 Kafka Collector 可以把 telemetry 数据先写入 Kafka，再由后续系统消费。

4. Prometheus：采集 Spring Boot Metrics

Prometheus 主要负责 metrics。Spring Boot 项目通常通过 Actuator 暴露健康检查和 metrics endpoint， 再由 Prometheus 定时 scrape。 

Spring Boot Actuator /actuator/prometheus
        ^
        |
Prometheus scrape

常见配置思路：

  • 应用引入 spring-boot-starter-actuator 和 Prometheus registry 依赖。
  • 打开 /actuator/prometheus endpoint。
  • Prometheus 配置 scrape target，例如 localhost:8080、localhost:8081。
  • Grafana 连接 Prometheus datasource，展示 JVM、HTTP latency、error rate 等 dashboard。

Prometheus 的定位不是查看单次请求的完整调用链，而是观察系统整体趋势。例如某个服务 5xx 错误率升高、 P95 latency 变慢、JVM memory 持续上涨。

5. Loki + Fluent Bit + Grafana：集中式日志

Loki 是 Grafana Labs 的日志存储和查询系统。Fluent Bit 是轻量级日志采集器。Grafana 是查询和展示 UI。 这套组合可以理解为日志方向的常见开源方案。 

Spring Boot logs
        |
        v
Fluent Bit
        |
        v
Loki
        |
        v
Grafana

各组件作用：

  • Spring Boot logs：应用把日志输出到 console 或文件，日志里最好包含 traceId 和 spanId。
  • Fluent Bit：负责采集容器日志或文件日志，解析、打标签，然后发送给 Loki。
  • Loki：负责存储和查询日志。它更强调 label 查询，而不是像 Elasticsearch 那样全文索引所有字段。
  • Grafana：连接 Loki datasource，用 LogQL 查询日志，也可以和 Tempo trace、Prometheus metrics 互相跳转。
如果日志里带有 traceId，就可以从一次 trace 跳到相关日志，或者从错误日志反查 trace。这是 logs 和 traces 联动排障的关键。

6. 其他常见 DevOps 设计

6.1 Grafana + Alertmanager：监控告警

只收集 metrics 还不够，生产环境通常还需要告警。Prometheus 可以根据 PromQL 规则触发告警， Alertmanager 负责分组、去重、静默和通知，例如发送到 Slack、Email、PagerDuty。 

Prometheus rules -> Alertmanager -> Slack / Email / PagerDuty

6.2 Kubernetes Health Checks：服务自愈

Spring Boot Actuator 的 /actuator/health 可以和 Kubernetes readiness/liveness probe 配合。 readiness 用来判断服务是否可以接流量，liveness 用来判断服务是否需要重启。 

Kubernetes probe -> /actuator/health -> restart or remove from traffic

这不是 tracing 工具，但它是微服务 DevOps 里非常常见的可靠性设计。

7. 推荐学习路线

  1. 先用 Zipkin 直接接 Spring Boot，理解 traceId、spanId、parentSpanId。
  2. 再引入 OpenTelemetry Collector，理解应用和后端解耦。
  3. 把 Collector 同时分发到 Zipkin 和 Jaeger，对比两个 UI。
  4. 进一步尝试 Tempo + Grafana，理解 Grafana 生态下 traces、metrics、logs 的关联。
  5. 最后接入 Prometheus 和 Loki，形成完整的 Observability 视角。

最终比较完整的目标架构可以是：

Spring Boot services
        |
        +--> traces  -> OpenTelemetry Collector -> Zipkin / Jaeger / Tempo
        |
        +--> metrics -> Actuator -> Prometheus -> Grafana
        |
        +--> logs    -> Fluent Bit -> Loki -> Grafana
        |
        +--> alerts  -> Prometheus rules -> Alertmanager
